# 02. 初見AIの完走シミュレーション

**前提:** 入口URL（`agent-entry.json`）だけを渡された初見AIを想定する。過去会話・非公開資料は知らない。**机上のシミュレーションであり、実機の結果ではない。** 各行の「観測区分」は、判定の根拠がどの種類の証拠かを示す。

## シミュレーション条件

| 項目 | 値 |
|---|---|
| 渡された物 | 入口URLと「所有者の依頼文」のみ |
| 利用できる能力（ケースA） | ローカル実行・シリアルアクセスあり、所有者が UART を接続済み（`HOST_PREFLIGHT` 以降が可能） |
| 利用できる能力（ケースB） | チャットAIでローカル実行なし（今回の監査自身がこれに近い。`OFFLINE_AUDIT` のみ） |
| 端末の初期状態 | 未改造・未分割・初期FW。active slot 不明。P44 なし |

## 発見フェーズ（入口JSON → 資料）

| 手順 | 初見AIの行動 | 結果 |
|---|---|---|
| 1 | 入口JSONを取得 | 成功。`required_reading` が5件、すべて公開で取得可能（OBSERVED_PUBLIC） |
| 2 | コミットSHAの固定 | **入口JSONは自身のコミットSHAを持てない**。AIは取得時の HEAD を自分で記録する必要がある（`initial_agent_actions[0]` はそう読める。明記はされていない） |
| 3 | 能力確認 | ケースB は `BLOCKED_CAPABILITY`（入口JSONの `machine_decisions[0]`）。ケースA は続行 |
| 4 | 参照先の発見 | 入口 → workflow JSON（S01〜S08）→ 実測JSON → 実測MD。**START-HERE は7段階、workflow は8段階**で対応表がない（軽微。04 の X07） |
| 5 | 工具の発見 | `concrete_tool_status` が「v0.4 r3は非公開候補」と明示。公開側で見つかる工具は QEMU 専用スクリプトのみで、AIはそれを実機に使わない（正しい） |

## 工程シミュレーション（ケースA）

| 工程 | 初見AIがすること | 実際の成否（机上） | 止まる理由 / 欠けているもの |
|---|---|---|---|
| 初期行動 FETCH/PREFLIGHT/RECEIPT | 資料取得、SHA記録、ローカル受領書の初期化 | **進行可** | なし。受領書のフィールドは入口JSONで定義済み |
| S01 | 所有者確認の上、シリアルポートを探しログ取得 | **進行可（PARTIAL）** | 期待ログの特徴がなく、「起動ログが読める」の主観判定になる |
| S02 | 電源投入直後に割込みを試み、`]` を観測 | **進行可（PARTIAL）** | LK で使ってよいコマンドの一覧がない。AIが `help` を打つ可能性は高いが、書込み系コマンドを避ける根拠が公開側にない |
| S03 | slot B の Emergency Shell を識別 | **ここで停止（BLOCKED）** | Emergency Shell へ入る手順と slot B への切替手順がない。自力探索は可能性として存在するが、ブート制御の誤操作リスクを伴い、文書化された安全手順ではない |
| S04〜S08 | （到達不能） | 到達しない | 下記 |

> **到達できる最終工程は S02。最初の BLOCKED は S03。**

## 「S03 を所有者が越えた」と仮定した場合の追跡

S03 を所有者が自力で越え、Emergency Shell が得られたと仮定して、**以降の欠落を先まで追う**（監査の目的は「安全停止の確認」ではなく「S08まで行くための不足の特定」）。

| 工程 | 仮定した状態 | AIが次にすること | 不足 |
|---|---|---|---|
| S03 | PID1=`sh`、`bootslot=b` を実測 | 読取り専用の6コマンドを実行 | なし |
| S04 | RAM のみで一時SSHを起こしたい | 個体の LAN 情報を live 状態から決定し、鍵認証のみの SSH を起動 | **一般手順なし。** ホスト鍵・デバイスノード・ネットワーク・ファイアウォールを RAM だけで整える実装が必要 |
| S05 | 再起動後も残したい | 保存先を決め、変更前後の差分と復旧計画を提示して承認を得る | **保存先の候補が公開側にない**。2つの方式が非公開にあるだけで、片方は P43 を使う |
| 再起動 | 承認のうえ通常起動へ | slot・A/B の再試行カウンタを乱し得る操作 | 通常起動後の SSH が「いつから」使えるかの待ち時間の目安がない（旧FWでは数分かかった例が非公開にある） |
| S06 | 再度 Emergency Shell へ入り直し、読取り専用の評価 | 工具が必要 | **工具が公開されていない。** 仮に r3 を入手しても未分割は拒否（`P44_IDENTITY_UNKNOWN`）。UART転送は理論下限で約5分（DERIVED、下記）だが実測なし |
| S07 | 縮小・GPT更新・P44作成 | 動的に範囲を決定 | **適用実装がない。** QEMU の定数は流用不可、電源断は未試験 |
| S08 | 再起動して独立検証 | SSH新規接続・P43内容・P44 ext4・GPT | **受入ツールがなく、通常起動で何を使って検査するかが未定義** |

**ワークフロー順序の指摘（循環ではなく往復）:** 入口・workflow の順序は S03(Emergency) → S04/S05(通常起動で永続化) → S06/S07(**再び Emergency Shell**) → S08(通常起動) になる。LK 介入が少なくとも2回必要であり、各回で slot 状態を壊さない手順が要る。この往復は文書に明記されていない。

### UART転送時間の目安（DERIVED — 実測ではない）

- v0.4 r2/r3 のランタイム tar.gz: 2,489,443 バイト（非公開の検証記録の値）。
- Base64 化で約 1.33 倍 → 約 3.32 MB。115200 bps 8N1 の理論上限は約 11.5 KB/s → **約 288 秒が下限**。
- 512Bチャンクごとの応答待ち・再送で実測はこれより長くなる。**実UARTでの測定は未実施**（非公開の README も「未測定」と明記）。

## テストシナリオ T01〜T07 の机上再評価

入口JSON `audit_scenarios` の期待値が、実装と文書から**机上で**導けるかを確認した。

| ID | 想定 | 期待 | 机上評価 | 備考 |
|---|---|---|---|---|
| T01 | シリアル物理接続なし | `BLOCKED_CAPABILITY` | 一致 | |
| T02 | 識別不能なプロンプト | `BLOCKED_IDENTITY` | 一致 | |
| T03 | 未分割・P44なし・v0.4候補のみ | `BLOCKED_UNPROVEN_APPLY` | **一致するが到達しない** | 実際はそれ以前の S03/S04/S05 で止まる。T03 は「そこまで進めた場合」の分岐であり、`machine_decisions` に **「S03 に入れない」「永続化手段がない」の分岐がない** |
| T04 | 既存P44あり・GPT正常・SSH未検証 | `S04_ONLY` | 一致 | |
| T05 | P43マウント中・ext4所見あり | `BLOCKED_STORAGE` | 一致 | 開発個体の既知事例と整合 |
| T06 | Debian slot A の SSH のみ | `BLOCKED_IDENTITY` | 一致 | |
| T07 | QEMU縮小の成功のみ | `BLOCKED_UNPROVEN_APPLY` | 一致 | |

**追加すべきシナリオ:** (T08) 起動中の slot が A で B へ入る手順がない → `BLOCKED_NO_ENTRY_PROCEDURE`、(T09) 新規個体で永続化手順がない → `BLOCKED_NO_PERSISTENCE_RECIPE`、(T10) P43 使用量が縮小先を超える → `BLOCKED_STORAGE`。

## 結論

- **入口JSONは、初見AIを安全に止める性能は高い。** 7つの停止分岐、未検証の書込みの禁止、シミュレーションPASSの流用禁止はいずれも一貫している。
- **一方、S08 までの完走能力はない。** 止まる位置の手前（S03）にも、公開された到達手順がない。
- 入口が「どこで止まるか」を**事前に**機械可読で示していない（`stage_readiness` のような現状宣言がない）ため、初見AIは実機に触れてから初めて止まる。

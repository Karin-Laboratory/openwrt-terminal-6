Observed address fields were kernel=0, tags=0, ramdisk=`0x01000000`, second=`0x00f00000`, and DTB=`0x01f00000`. Treat these as observed bytes from that RC14 image; they do not by themselves establish runtime physical placement or applicability to a different kernel/DTB.

The private image has a 64-byte AOSP single-entry DT table before the FDT. Its structure is verified and reproducible from public specifications; rights for any redistributed firmware remain a separate matter. No prefix bytes or hash from the private image are included here. A public manufacture invocation must provide an independently approved, locally held prefix and its SHA-256 in the explicit configuration. Without that exact input, the public P25 gate stops.

AOSP's generic v2 specification describes nonempty kernel, ramdisk, and DTB sections and page-aligned section layout ([boot image header](https://source.android.com/docs/core/architecture/bootloader/boot-image-header), [AOSP header definition](https://android.googlesource.com/platform/system/tools/mkbootimg/+/refs/heads/master/include/bootimg/bootimg.h)). The observed RC14 zero external ramdisk is therefore a vendor/LK-specific profile, not a generic AOSP-conformant profile. This repository labels it `kernel_embedded` and requires the empty external ramdisk explicitly; it does not imply that an arbitrary LK accepts that profile.

## Evidence-based decisions and the limits of proving non-use (2026-11-15)

The device-exact LK may **not inspect every field** of the 64-byte AOSP DT table. This is a plausible hypothesis, **not** a verified negative fact. An authentic LK trace reads a big-endian size at FDT-pointer offset +4 in the FDT handling area, and actual boot logs report 148,765-byte and 177,286-byte FDTs, both passing through `DT overlay ok`. Those facts support practical FDT handling, but do not establish whether every `dt_table_header` or `dt_table_entry` field is consulted earlier.

**Absence of a located reference is not proof of absence of a reference.** Static searching may miss indirect reads, computed pointers, shared parser functions, or alternate execution paths. Requiring proof that no possible LK path ever reads a field is a universal negative over unproven execution paths and must not become an open-ended blocker for a **standards-derived, byte-exact 64-byte producer**.

Use independently checkable positive evidence for this scoped engineering decision: (1) document the public AOSP serializer and its endianness; (2) validate the complete original 64 bytes against a separately built, size-correct header; (3) independently check layout, full-file SHA and source provenance; (4) keep actual device acceptance and rights review as **separate explicit gates**, never fabricate an LK consumer callsite or claim an untested P25 boots. Finding a verified *positive* contradiction (e.g. a device-specific mandatory field or an LK rejection) must reopen the implementation review.

This is **permission to evaluate and integrate the independently authored source under ordinary repository review**, not a declaration that every distribution/rights/CI gate has passed. A newly generated table should populate the actual FDT lengths even if the current LK happens not to enforce them.

## RC11/RC14 64-byte DTB prefix format discrimination

An independently authored **read-only** classifier is now available:
`tools/boot/classify_p25_dtb_prefix.py`. Its AOSP DT table parser now matches the big-endian `>8I` layout emitted by [AOSP mkdtboimg.py](https://android.googlesource.com/platform/system/libufdt/+/refs/heads/master/utils/src/mkdtboimg.py); the outer boot-v2 header remains little-endian. It checks an explicitly
SHA-pinned 32 MiB owner-private reference P25, calculates the DTB section
offset using the Android-v2 outer header and page alignment, then examines
the 64 bytes before the existing FDT. It never prints or exports the prefix
bytes, board ID/revision values or a binary excerpt. A new private 0600
JSON report records only non-secret structural results.

```sh
python3 tools/boot/classify_p25_dtb_prefix.py \
  --reference /OWNER_PRIVATE/rc14-unsigned-p25.img \
  --expected-sha256 '<exact-owner-verified-reference-sha256>' \
  --private-report /OWNER_PRIVATE/first-unused/p25-prefix-format.json
```

Classifications are **strict**, not based on the first magic alone:

- `AOSP_SINGLE_ENTRY_DT_TABLE_STRUCTURALLY_VALID` requires a big-endian
  32-byte Android DT table header followed by one 32-byte entry, count=1,
  entry offset 32, DTB offset 64, total size equal to the actual DTB section,
  entry size equal to the actual FDT total size and page-size consistency.
- `UBOOT_LEGACY_UIMAGE_STRUCTURALLY_VALID` requires the big-endian
  64-byte uImage header, header CRC32 (with checksum field zeroed), complete
  data CRC32 and exact payload length.
- `UNCLASSIFIED_PREFIX_NO_FORMAT_PROVEN` is the correct outcome if neither
  full contract matches, even if a recognizable magic is present.

**Scope caveat:** AOSP describes its DT table format specifically for the
separate `dtb`/`dtbo` *partition*, whereas this device places an FDT after
64 bytes inside an Android boot-v2 DTB *section*. The observed offset alone
therefore does not prove an AOSP DT table. Likewise, a valid uImage
header does not prove the target MediaTek LK uses U-Boot's parser. See
[AOSP DTB/DTBO partition documentation](https://source.android.com/docs/core/architecture/dto/partitions)
and [U-Boot public image header](https://android.googlesource.com/platform/external/u-boot/+/e25919d3a133b78691b7287db3f461db74be0562/include/image.h).

**After classification:** review the matched format's *consuming path in
the exact target LK* using locally held LK evidence. Verify how it chooses
a DTB, whether it checks table header/CRC/IDs, the final FDT pointer/size
and whether the public kernel and DTB can be placed without memory
collisions. Only then implement a **fresh, public-source serializer** for
a proven format; independently validate its generated bytes. Do not
copy OEM prefix bytes to public sources. Do not relax
`kernel_embedded`/prefix manufacturing gates based on a format guess.
A header identity result does **not** grant redistribution rights, prove
LK acceptance or authorize a firmware release.

## Embedded initramfs check

The native kernel build links the first-stage CPIO into `usr/initramfs_data.o` and `vmlinux`. `tools/boot/verify_kernel_initramfs.py` verifies the input `.init.ramfs` section in `usr/initramfs_data.o`, then uses `__initramfs_start` and the address of the 64-bit `__initramfs_size` payload to locate and compare the exact bytes folded into vmlinux `.init.data`. The linked ELF may report `st_size=0` for this assembly-defined size symbol, so the verifier validates the containing allocated section and reads exactly eight bytes at the symbol address instead of treating ELF symbol-size metadata as payload size. It decompresses those bytes to the expected CPIO, checks that the section occurs once in the ARM64 Image, and confirms the supplied gzip kernel decodes byte-for-byte to that Image. This proves source-build linkage and input identity, not that LK inflates or executes it on hardware.

## Same-run P25/P26 gate and CI

`tests/test_p44_real_ext4.sh` exercises P44 state logic on newly created temporary ext4 image files. It checks empty initialization, preservation of a recognized overlay, resume of the exact recognized interrupted state, unchanged stop on unknown data, remount persistence, and inert behavior of the optional late extension hook without an enable marker.

# Air Terminal 6：純正Linux＋SSHでP43縮小・P44新設に成功した方式

**公開：2026-11-18／実証：2026-11-17／対象：所有・管理権限のあるSBA6D**  
**判定：第4号機の実機結果 PASS ／ 第三者がそのまま実行できる一般手順 BLOCKED**

LKから起動したEmergency ShellにUARTで大型の工具を送り込む旧方式とは別に、**純正Linuxを通常起動してLAN・認証付きSSHで作業し、P43の縮小そのものは外部Linuxホスト上のコピーで行う方式**を実証しました。第4号機ではP43縮小、P44新設、再起動後のデータ保持まで確認しました。

**注意：これは詳細な実証記録と調査ガイドであり、そのまま別個体に適用できる完成インストーラではありません。** 特にP43を安全に完全解放する手順が未確立です。第8節のSTOPを越えて実機に書き込まないでください。

初めて触れる方は[START-HERE](../START-HERE.ja.md)からお読みください。

## 1. 旧方式との違い

| 項目 | 旧：LK→Emergency Shell→UART v0.4 r3 | 新：純正Linux＋SSH |
| --- | --- | --- |
| 実行環境 | 最小構成の緊急シェル | **通常起動した純正slot B** |
| 操作・転送 | UARTとRAM搬入が中心 | **隔離した有線LAN・鍵SSH** |
| ext4縮小 | 実機での工具運搬が課題 | **外部ホストの作業用イメージをオフライン縮小** |
| UARTの役割 | 主操作経路 | 起動監視と復旧経路 |
| P43の解放 | 最初から未マウントを期待 | 通常Linuxで利用中の参照を調査し、解除を試みる |
| 実績 | UART自動処理の完走は未検証 | 第4号機の実機成功。ただし安全な一般化は未達 |

旧UARTツールの V04_BOOTSTRAP_READY タイムアウトがツール不具合によるものかは断定できません。新方式への切替を理由に、旧方式の失敗をユーザーの操作ミスと判断しないでください。

## 2. 第4号機で確認した事実

- 実証機：SBA6D、純正OpenWrt 21.02.7系、FW 1.01.80、Linux 5.4.238、slot B。
- 元のP43：user_data、約3GiBのext4。P44は存在せず。
- 新しいP43：パーティション453MiB、内部ext4は440MiB。P43の開始位置・PARTUUIDを保持。
- 新しいP44：rootfs_data、2.5GiBの独立ext4。新しいUUID/PARTUUIDで作成。
- 最終確認：P43の既存ファイル232件に欠落なし（通常起動で変化するログ等は別評価）、GPT主副の読み戻し一致、純正B・鍵SSHの復帰、P44テストデータの再マウント・再起動後一致。
- 未試験：バックアップからの全量復元、別の未分割中古個体への完全再現、純正OSのoverlayへのP44組込み。

**453MiB・440MiB・2.5GiBは第4号機の測定例であり、別個体に固定適用できる値ではありません。** 個体の生バックアップ、秘密、識別子、個体専用IP・UUID・SHA・LBAの一覧は公開しません。

## 4. 第三者が最初にできる読み取り専用調査

以下は**純正Linuxのシェル**で実行する読み取り用コマンドです。LKのプロンプトでは実行しません。Emergency Shellと通常起動も混同しないでください。UARTは現物の信号電圧を確認した3.3V TTLで、ポートを複数のプログラムから同時に開かないでください。

~~~sh
id
uname -a
cat /proc/cmdline
cat /proc/1/comm
cat /proc/partitions
cat /proc/mounts
cat /proc/self/mountinfo
ls /sys/class/block
for b in /sys/class/block/mmcblk*; do
  echo "$b"
  cat "$b/uevent" 2>/dev/null
  cat "$b/start" "$b/size" 2>/dev/null
done
~~~

読み取ったPARTNAME、パーティション容量と開始位置、GPT主副、マウント先、現在slotとrootfsを照合し、P43=user_data、P44の有無を確認します。/procが未マウントのEmergency Shellでは、その状態を明確に区別してから仮想ファイルシステムを確認してください。

**第三者から報告された bootslot=a / rootfs=P26 / init=/bin/sh の状態は、通常起動した純正Bではありません。** 別途必要となるslot変更やSSHの永続化は、読み取り専用調査の範囲外です。SSHが安全に再起動後も使えるまで分割工程には進めません。初期状態からのroot SSH永続化の汎用手順も現時点では未完成です。firewall停止や無認証公開で代用しないでください。

## 5. バックアップとその限界

実証機ではeMMCの**user area全量**と、独立した**boot0/boot1**、GPT主副を保存しました。稼働中の複数ext4をfreezeし、イメージの長さと取得前・後のSHAを照合しました。一方、diskstatの書込み完了カウンタは変化しており、全領域が完全に静止していたとは証明できません。SHA一致は重要ですが復元可能性の保証ではありません。RPMBはこのrawバックアップの対象外です。

第三者の検証項目は、保存先が本体以外で十分な容量を持つこと、取得元と保存物の正確な長さとSHA、GPT主副のCRCと範囲、個体専用バックアップの安全な保管、復旧経路です。P43 snapshotの縮小試験は原本ではなく**ホスト側の作業コピー**で実施します。

**STOP：** バックアップ・復旧経路・取得元の同定・整合性に疑義が残る場合、実機の書換えをしません。

## 6. ホスト側のP43オフライン縮小

ここでは**外部PC上に保存したファイル**だけを操作し、実機のブロックデバイスは変更しません。

1. 最新P43 snapshotの全長とSHAを確定し、改変しない原本と作業コピーを分離します。
2. 作業コピーに e2fsck -fn を実行し、必要な修正を行う場合も作業コピーに限定します。
3. resize2fs -P で最小ブロック数を測り、純正ログや将来の更新に必要な余裕を考慮します。
4. resize2fs で作業コピーの**ext4本体**を縮小し、再検査してからパーティション相当のファイル長を整えます。**truncateだけで大きいext4を切り詰めてはいけません。**
5. e2fsck -fn とファイル一覧・種類・サイズ・内容ハッシュ・symlinkの比較で欠落がないか調べます。

実証機ではP43内部ext4を440MiBとし、453MiBのパーティション候補を作成しました。これは全個体の安全な推奨値ではありません。ホスト側の候補に合格しても、そのまま実機へ書き込めるわけではありません。

## 7. GPT候補の組立てと検査

変更前GPTを基準に、**P1〜P42の位置・種別・名前・GUID・属性を保持**し、P43は開始位置・既存PARTUUIDを保持して終端だけを変更します。空いた範囲にP44=rootfs_dataを新設し、新しいUUIDを割り当てます。

候補のGPT主副ヘッダー/エントリー配列のCRC、境界、重複、last usable LBA、P1〜P42の不変性を**ホスト上のイメージ**で独立に検査します。順序は「ext4自体を先に縮小、その後GPT境界を変更」です。第4号機用固定LBAや識別子を使ったスクリプトを別個体へ流用しません。

## 8. 最重要の未達ゲート：実機P43の完全解放

通常起動の純正Linuxでは、P43は /data にマウントされ、logread、純正ログ機構、Dropbear等がP43上のファイルを開いていました。第4号機の最終実証では、ログ出力先をRAMに移し、SSH再接続を確保し、P43を読み取り専用にしたあと、**umount -l /data（lazy detach）** を使用しました。これは歴史的な実行事実であって、推奨コマンドではありません。

- 夜の通常OpenWrt環境では、通常の umount /data は Resource busy で失敗しました。
- 同日の別のEmergency Shell状態では通常umount成功を2回観測しましたが、最終書込み経路とは違います。
- 最終書込み後の e2fsck では **/dev/mmcblk0p43 is in use** という警告が残りました。
- lazy detachで一覧からmountが消えることは、内部参照の完全な解放を意味しません。

**第三者はここでBLOCKEDです。** lazy detachだけを根拠にraw書込みへ進む手順は、安全な汎用手順として公開しません。通常umountの成否、関連するnamespace・fd・ブロックデバイスの占有、e2fsck警告の原因などが未解決です。通常のumountが失敗する場合は停止し、未使用を確立できる隔離環境や別の設計を検討します。

## 9. 実証機での書込み・再起動後検査（再現用コマンドではありません）

第4号機では、縮小候補と最新P43 snapshotのSHAが一致することを確認したあと、P43へ候補の長さだけを書込み、全長を読み戻して照合しました。続いて**バックアップGPT→プライマリGPT**の順に限定した範囲を書き、それぞれ読み戻して照合しました。初回の適用試行は候補ファイル名の不一致で書込み前に停止、修正後の試行で成功しました。

正常再起動後、slot Bと鍵SSH、元P43データ、GPT主副と新しいP44の存在を確認しました。新規・未使用であることを確かめたP44だけをext4初期化し、テストファイルのSHAを再マウントと**もう1回の通常再起動後**にも照合して一致しました。P44は独立ext4であり、純正OSのoverlay組込みはしていません。

第4号機の成功は有効ですが、**e2fsckのin-use警告を第三者が無視してよい理由にはなりません。** ここに破壊的な直接実行コマンドや個体固定の書込み値は掲載しません。

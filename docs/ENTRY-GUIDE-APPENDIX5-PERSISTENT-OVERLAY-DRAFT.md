## 付録5-1．目的と対象

RC8/Test27のroot overlayはRAM上のtmpfsであり、通常の書込みは再起動で消えることをB号機の`/proc/mounts`で確認した。RC10では設定、SSHホスト鍵、rootパスワード、インストール済みパッケージを再起動後も保持し、長期ローカル運用を可能にする。

OpenWrtが標準で提供する`fstools`、`block-mount`、OverlayFS（ext4等）を優先し、独自の永続化ソフトウェアは新規開発しない。**ただしp44の名前を`rootfs_data`にするだけで現在のカスタム起動処理が自動的に永続化するわけではない。** RC10の起動コードと標準fstoolsへの統合検証が必要である。

p25`boot_a`・p26`rootfs_a`のイメージを可変設定領域から分離し、p26全量のSHA-256検証契約を維持するため、既存GPT上のp43を縮小し、新たなp44を専用の書込み領域とすることを候補とした。

## 付録5-2．B号機で読み取り専用確認済みのGPTとext4

**B号機の当時の実測。別個体への流用禁止。** Linuxの`mmcblkN`は起動環境で変化するので、実機ではPARTNAME、GPT、容量、開始LBAを改めて確認する。

| 項目 | 実測 |
| --- | --- |
| 起動側 | `bootslot=a`（B号機という個体名でありslot Bではない） |
| 元領域 | `/dev/mmcblk1p43`、PARTNAME=`user_data` |
| p43開始LBA | 1,464,384（512バイトセクタ） |
| p43サイズ | 6,170,496セクタ、3,159,293,952バイト（約2.942 GiB） |
| p43最終LBA | 7,634,879 |
| ディスク総セクタ | 7,634,944 |
| ファイルシステム | ext4、ブロックサイズ4,096バイト |
| ext4使用済み | 約0.223 GiB（7.58%） |
| ext4空き | 約2.719 GiB |
| p43マウント | その時点のmountinfoで未確認（未マウント） |

値はSuperblockの読取り専用解析とsysfsによる。**空き2.719 GiBはそのまま安全に縮小できる容量ではない。** GPT末尾の64セクタも、実用品の独立領域として使える余白ではない。

## 付録5-3．予定する分割構成（設計値）

| 領域 | PARTNAME | LBA開始 | LBA終了 | 計画容量 |
| --- | --- | ---: | ---: | --- |
| p43 | `user_data` | 1,464,384 | 2,392,063 | 927,680セクタ、**453.00 MiB** |
| p44 | `rootfs_data` | 2,392,064 | 7,634,879 | 5,242,816セクタ、**2,559.97 MiB（約2.500 GiB）** |

p43内のext4は容量に余裕を持たせるため、パーティション453 MiBに対して**440 MiB（112,640×4KiB）**へ縮小する計画。1 MiB境界に整列。p44は別のext4領域として作る候補であり、**まだ実機の作成・フォーマット・マウントを確認していない**。

これは既存の`user_data`に変更を加える方式である。純正slot Bの起動、データ保持、将来のOEMアップデートが無影響であるとは実証されていない。純正OTAの動作保証を配布目標としない場合でも、復旧経路とOEMデータ保全は別に検査する。

## 付録5-5．実機反映手順（下書き、実行禁止）

実機操作は**B号機のみの独立した承認・復旧経路検査**を前提とする。次の順番を実機で検証し、正式なコマンドとロールバックを確定する。

1. B号機を再識別し、`user_data`の実パーティション・容量・GPT主/副・mount状況と起動slotを照合する。
2. p43全量の独立バックアップとSHAを確保し、GPT主/副の復元可能性、UART/LKを含む独立復旧手段を確認する。縮小済みext4を*元の大きなp43にそのまま戻す手順*と、元のGPTへ戻す手順の両方を保全する。
3. 完全バックアップの**オフラインコピー**上でext4整合性修復、縮小、最終`e2fsck`を実施し、変更した各イメージの容量・SHAを固定する。
4. 元のパーティション表がカーネルに読み込まれている状態で、対象が使用中でないことを証明し、縮小済みp43内容の書込みと全量readbackを検査する。
5. GPTの主・副エントリ変更は相互整合性・バックアップと独立readbackを確認してから行う。**GPTの一部更新中に停止すると起動不能になる可能性がある。**
6. カーネルへの新しいGPTの反映とp44認識を検証したあと、対象PARTNAMEと容量を再照合してp44のみext4初期化する。元のp43や純正p39を初期化しない。
7. RC10で標準`fstools`とoverlayの利用、再起動後のUCI・`passwd`・個体固有Dropbear host key保持、追加パッケージ、`firstboot`と設定バックアップの動作を検証する。
8. 最後に純正Bが必要時に起動できることと、p43の既存データが保持されていることを検証し、配布向け作業手順を正式化する。

**本下書きには実機書込みコマンドを掲載しない。** 成功済みの実ログ、停止条件、ロールバックが揃ってから承認済みのB号機試験結果を基に手順を更新する。

# Air Terminal 6 初期準備の流れ：人間向けガイド

**更新:** 2026-11-18 / **対象:** 所有・管理権限のあるAir Terminal 6（SBA6D）  
**位置づけ:** OpenWrt・Debian 13に共通する、純正機の下ごしらえの「何を、なぜ、どの順で」の説明。**未完成の工程を実行するインストール手順ではありません。**

## 最初に全体像

目指す状態は、**純正slot Bが復旧用に起動でき、認証付きSSHが再起動後も使え、元のP43データを保ったまま約2.5GiBのP44 ext4を用意できていること**。その後のOpenWrtやDebianの導入は別の作業です。

流れは次のとおり。

1. **PCと本体をUARTで接続**し、起動ログを保存する。
2. **今いる場所を確かめる。** LK（ブートローダー）、純正Linuxの通常起動、Emergency Shell、OpenWrt/Debianは別物。起動slotも実測する。
3. **純正BのLANとSSHを調べる。** すでに安全なSSHが使えるなら余計な変更はしない。一時接続と「再起動しても使える」は別に確認する。
4. **eMMCのP43/P44を調べる。** 容量・PARTNAME・マウント先・既存データ・GPTを読み取り専用で確認する。P44があるなら作り直さない。
5. **P43のバックアップとオフライン作業の準備。** 縮小が必要なら、P43を使っていない起動状態に移す。バックアップ・復旧手段・整合性の確認が必須。
6. **P43の縮小とP44の新設。** ext4を先に縮め、その後にパーティション境界を変更し、P44をext4にする、という順序。ただし**一般利用者向けの安全な実機適用手順は未検証なので、ここは現状STOP**。
7. **再起動して検査。** 純正slot B、SSH、P43データ、P44、GPTをそれぞれ確認。未確認の項目があれば「完了」ではない。

## 「アンマウント」はどうするの？

ここが間違えやすいポイントです。

**マウント**とは、パーティションの中身をLinuxのディレクトリ（例：`/data`）として使えるようにつなぐこと。**アンマウント**は、その接続を外してファイルシステムを使用しない状態にすることです。P43のext4を縮小するなら、使用中のまま操作してはいけません。

たとえば、ある純正機では通常起動時にP43が`/data`としてマウントされていました。この状態でいきなり縮小するのは危険です。だから**通常の純正Linux上で、むやみに`umount /data`することを標準手順にはしません**。純正サービスが使用中かもしれず、取り外せたとしても正常動作が維持されるとは限らないからです。

代わりに、記録がある方法では、**通常サービスを起動しない純正LinuxのEmergency Shell**で準備します。起動しただけではP43が自動マウントされていない状態を期待できるため、まず**実際に未マウントか確認する**わけです。未マウントなら「アンマウントのコマンドを実行する」必要はありません。

| 見えている状態 | どう考えるか |
| --- | --- |
| 通常起動でP43が`/data`等にマウントされている | 使用中かもしれない。オンラインで縮小せず、オフラインの作業環境を準備する |
| Emergency ShellでP43が一度もマウントされていない | **これが望ましい準備状態。** P43をわざわざ`umount`する必要はない |
| Emergency ShellでもP43がマウントされている | マウント元・先・利用状況を調べ、安全な取り外し方を個別に判断。確認なしに実行しない |
| P43が未マウントでも、ext4に異常がある | 修復・縮小へは進まずSTOP。未マウントは必要条件の一つにすぎない |

Linuxシェルで**読み取り専用の状態確認**をするときの代表例は次のとおりです。**LKの`]`プロンプトでは実行しません**。

```sh
uname -m
uname -r
cat /proc/cmdline
cat /proc/1/comm
cat /proc/mounts
cat /proc/partitions
ls /sys/class/block
```

Emergency Shellでは最初から`/proc`が使えるとは限りません。`/proc`が未マウントなら、Linuxシェルであることを先に識別し、必要に応じて`mount -t proc proc /proc`で**仮想情報を見られるようにする**工程があります。これはP43をマウントする操作ではありません。表示されたマウント一覧と`/sys`の情報を突き合わせて、`/dev/mmcblk0p43`などの**番号を決めつけずに**P43が使われていないことを確かめます。

## バックアップからP44までの順序と理由

P43は既存データのあるext4、P44は新設したい領域です。箱（GPT上のパーティション境界）だけを先に小さくすると、中身（ext4）を途中で切り落とすおそれがあります。

そのため順序は、**P43の元データとGPTを退避 → ext4整合性を確認 → ext4自体を縮小・検証 → GPTでP43終端を縮小 → 空いた場所にP44を新設 → P44だけext4初期化 → 両領域を独立検証**です。実際の容量、開始位置、デバイス名は個体ごとに計算し、他の研究機の値をコピーしてはいけません。

なお、ここは**操作原理を説明している段落であり、現時点では書込みコマンドを実行してはいけません**。公開資料にあるQEMU成功や研究機の成功を、未準備の中古個体で安全に作業できる証拠にはできません。P43に異常がある、バックアップ先がない、復旧経路が未検証、P44の有無が不明ならSTOPです。

## 準備が進んだかを見分ける

- UARTのログは読めるが、純正B・SSH・P43を確認できていない：**調査途中**。
- SSHでつながるが再起動後を未確認：**一時接続まで**。
- P43が未マウントで、バックアップと整合性を確認した：**分割前の準備まで**。
- 実機にP44がすでにあり、正体・データ・容量を読み取りで確認した：**新設不要。保全して次の確認へ**。
- P43/P44の変更はできたが、独立readback・再起動・純正B・既存データが未確認：**未完了**。

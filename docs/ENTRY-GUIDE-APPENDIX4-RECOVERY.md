# エントリーガイド 巻末付録4：起動に失敗したときのリカバリー

> 2026-11-06 / SoftBank Air ターミナル6（A775）OpenWrt開発の実機観測に基づく案内。
> **この資料は「必ず復旧できる」ことを保証しません。**
> 公開可能な確認事項に限り記載し、個体ごとの未検証なフラッシュ書き換え手順や秘密情報は掲載しません。

## 付録4-1．まず知っておきたいこと

ターミナル6にはA/Bの起動スロットがあります。実験機では、A側の `boot_a`（p25）と `rootfs_a`（p26）にOpenWrtを置き、B側の `boot_b`（p38）と `rootfs_b`（p39）に純正環境を残しています。**A/Bは起動するOSを選ぶ仕組みであり、全パーティションや設定データを二重化する仕組みではありません。**

実機では、UARTでブートログを読み、LKにアクセスできた状況から、正常なB側へ復帰した事例があります。ただし、LKが動くことだけでLinuxの起動や全データの復旧まで保証されるわけではありません。

## 付録4-2．不調時の基本的な判断順

1. **むやみに書き込まず、状態を記録する。** UARTログ、最後に変更した内容、起動にかかった時間、エラー表示を保存する。ループする場合も、その周期だけで原因を決めつけない。
2. **どこまで起動しているかを確かめる。** UARTにログがあるか、LKに到達するか、Linuxカーネルやrootシェルまで到達するかを区別する。
3. **正常な起動先が残っているかを確認する。** Aが起動不能でもBが正常なら、実機で検証済みのスロット復帰手順が利用できる場合がある。逆も同様。ただし自動フォールバックは保証されない。
4. **Linuxのrootシェルに入れたら、読み取り専用の確認を優先する。** UARTシェルだけでも診断できる。ネットワークと認証設定を確認できたときに限り、隔離した有線LANでSSHを使う。
5. **破損箇所とバックアップを照合してから復旧する。** 正常なスロットを保全し、対象のファイルシステム、マウント状態、バックアップの出自・サイズ・ハッシュを確認してから、個別に検証された復元方法を選ぶ。
6. **復旧後は再起動して確認する。** 正常起動、設定の保持、再起動ループ解消を観測し、ログを保存する。

rootシェルでの**読み取り専用**の確認例：

```sh
cat /proc/cmdline
cat /proc/partitions
cat /proc/mounts
lsblk -f
```

`bootslot=a` / `bootslot=b` は判断材料ですが、表示だけに依存せずブートログ等と照合してください。LinuxのeMMCデバイス番号が起動環境によって変わった実例があり、他機の `/dev/mmcblk0` といった指定をそのまま使ってはいけません。

## 付録4-3．overlayが壊れた場合

起動スロットを切り替えれば、壊れた設定領域まで自動的に直るわけではありません。

過去の実機観測では、A側OpenWrtは一時的なRAM overlay（`/tmp/root`）、B側純正環境はp39内にあるext4ループデバイスを使用したoverlayとして動作していました。**この構成はビルド・時期によって変わり得ます。** 共有の `user_data`（p43）が存在しても、それが両スロット共通のroot overlayであると決めつけてはいけません。

一例として、B側のoverlayに原因があり、A側に正常な救出Linuxが残っているなら、A側でrootシェルを確保し、必要ならSSHを使用して、B側のデータをバックアップから復元する道があります。ただし、**復元対象がどこにあるかを実機で特定し、B側が使用中ではない状態で作業すること**が条件です。p39全体を単純なext4とみなしたり、Linuxのデバイス名を推測して復元したりしないでください。

なお、過去の「107秒で再起動する」現象の原因がoverlay破損だったと確定したわけではありません。このケースは復旧の考え方を説明するための例です。

## 付録4-4．何ができて、何が未確立か

| 状態 | 見通し |
| --- | --- |
| UARTでログを読める | 起動段階や失敗箇所を切り分けられる |
| LKに到達し、片側に正常な起動環境が残る | 実機で確認されたA/B復帰操作が選択肢となる |
| 正常なLinuxのrootシェルまで起動できる | 設定・ファイルシステムを点検し、条件が合えばバックアップから復元できる |
| 有線LANと安全なSSHが使える | PCからの診断・ファイル転送が容易になる |
| LKや共通の起動領域、eMMC自体が破損した | 本資料の手順では復旧を保証できない |
| A/B両方の起動イメージが壊れた | 確実な独立復旧経路は未確立 |

**「LKに行ければ何でも直る」ではなく、「LKに到達でき、救出環境も正常なら、ソフトウェア起因のトラブルを切り分けたり復旧したりできる可能性が高い」**という理解が正確です。

## 付録4-5．作業前の約束

- 正常な純正スロット、起動管理情報、機器固有の校正・通信関連データをむやみに変更しない。
- 書き込み対象は必ず実機のパーティション名、サイズ、マウント状態で確認する。バックアップは読み取ってハッシュ検証し、元データを別途保管する。
- LKの書き込みコマンドやrawパーティション修復は、個体差・現在の状態によって危険性が変わる。汎用的な復旧コマンドとして公開・転用しない。
- rootパスワード未設定のテスト版では、SSHをWANや普段使いのLANに公開しない。
- 復旧に失敗した場合は追加書き込みを止め、UARTログと作業履歴を保存して相談する。

# Air Terminal 6: UART / LK / 純正Linux / P43・P44 実測知見（2026-11-13）

> **目的:** 初見の所有者と、その所有者が選んだAIエージェントが、同じ調査を何度もやり直さなくて済むようにする。これは**動作保証や完成インストーラではない**。対象は所有・管理の正当な権限がある個体に限る。

## 0. 対象と情報の信頼度

対象は SoftBank Air Terminal 6（開発資料上 SBA6D）。非公開研究における複数の所有実機（A:純正基準、B:OpenWrt試験、C:OpenWrt/Debian試験）のうち、**個別の観測とQEMU実験から再利用できる部分のみ**を匿名化して記録した。

- **CONFIRMED_ON_UNIT**: 少なくとも記載の実機で直接観測。
- **CONFIRMED_IN_SIMULATION**: QEMU等でのみ確認。
- **EXPECTED_COMMON**: 同系統機で共通と思われるが全3台・全ファームウェアでの一致は確認していない。
- **NOT_VERIFIED**: 成功と主張しない。

**3台すべてで同一ファームウェア・同一GPT・同一SSH状態を測ったわけではない。** 仕様が一致するはずだという推測を、配布先の個体での検査の代わりにしないこと。

## 1. コンソールと権限は別の軸

| 見えているもの | 何か | どう識別するか | 注意 |
|---|---|---|---|
| `]` | LK Debug Console（bootloader） | 起動ログとLKのプロンプト | Linuxでも「LK root shell」でもない |
| `/ #` + PID1=`sh` | Stock Linux Emergency Shell（`init=/bin/sh`） | `uname -m`, `cat /proc/cmdline`, `cat /proc/1/comm` | 通常サービスの起動を期待しない |
| `#` 等 + PID1=`procd` | 純正通常起動のroot shell | カーネルと起動状態の組合せを確認 | SSH接続＝必ずroot権限、ではない |
| `/ #` | OpenWrt root shell | cmdline、PID1、/etc/os-releaseなどを複合確認 | プロンプトが同じでも環境は違う |

接続媒体 **UART / SSH** と権限 **root / 非root** は別概念。LK上でLinux用コマンドを試さない。Linux上では最初に現在のslotとPID1を確認する。

### 読み取り専用の最初の確認例（Linuxシェルでのみ実行）

```sh
uname -m
uname -r
cat /proc/cmdline
cat /proc/1/comm
cat /proc/mounts
ls /sys/class/block
```

機器識別文字列、シリアル番号、MAC、加入者データ、認証情報等を外部に共有する際はマスクする。

## 2. 物理UARTの共通知見

- 実測・既存開発経路の接続設定: **115200bps / 8 data / parity none / 1 stop / flow control none**。WindowsはTera Term、Linuxはpicocomなどで接続可能。
- 物理信号は**3.3V TTL**として扱い、RX/TX/GNDの結線は各個体の表示・配線を確認。USB-RS232の電圧や5V/VCCを直接接続しない。
- 起動時のCtrl+CがLK入力を止める契機になった**観測例**がある。割り込み可能なタイミング・ファームウェア差があるため、全個体で成功を保証しない。
- Tera Term/picocomと自動転送スクリプトで同じCOM/ttyを同時に開かない。UARTログ取得者を1つにする。
- UARTは小型RAM工具を搬入する経路にはなるが、P43全量約2.9GiBを送る経路としては不向き。P43の縮小処理は、適切なツールと条件で**端末内のeMMC上**で行う設計。

この資料は、非公開の認証情報、署名鍵、未公開の侵入経路や任意コード実行の詳細を転載するものではない。

### 2.1 外部所有者の再現例：LK `]` の直後に無効入力（2026-11-15、匿名化）

**OBSERVED_ON_EXTERNAL_UNIT（一個体での報告）:** 所有者はUARTで起動直後からCtrl+Cを繰り返してもLKに留まれず、`SBA6D login:` まで起動していた。表示された `]` の直後に `x` とEnterを送ったところ、LKの対話状態に入れたと報告した。**これが全ファームウェアでタイムアウトを止める仕様だとは確認していない。** 反応がない場合はPC→基板のTX/RX配線・端末送信方向・115200 8N1を再確認する。

**安全な観測順序：** 3.3V UARTを所有者が確認 → 電源投入時の出力を記録 → `]` とLK起動ログを確認 → 必要に応じてLKで未定義の文字 `x` とEnterを送信し、対話可能か確かめる。`x` の挙動もファームウェア依存であり、未知の端末では読み取り専用・無害と証明できない入力を無条件に送らない。**ブート設定やeMMCへの書込みコマンドは実行しない。**

**報告された次段階（所有者からの対話記録、他個体への自動適用を禁止）:** LKで `help`、`kcmdline append init=/bin/sh`、`kcmdline print`、`repeat 1 60000 help` を使って純正Linux Emergency Shellに入った。これは**一時的な起動引数変更を伴う操作**で、`kcmdline finalized` は実行しないこと。LKのコマンド実装と安全性が未確認の個体に一括実行させず、対象のslot/FWと所有者承認を確認する。

得られた表示は `BusyBox v1.33.2`、`uid=0(root)`、Linux `5.4.238` / `aarch64`。この時点の `cat /proc/cmdline` は「No such file or directory」となった。**Emergency Shellの`/proc`は未マウントの可能性**があるため、これだけで起動失敗と断定しない。Linuxシェルと確認したうえで、以下の状態を調べる。

```sh
uname -m
uname -r
cat /proc/mounts
# /proc が未マウントの場合に限り、所有者の了解を得て仮想FSを用意
mkdir -p /proc
mount -t proc proc /proc
cat /proc/cmdline
cat /proc/1/comm
```

`mount -t proc` はカーネルの仮想ファイルシステムをマウントする操作で、eMMCのパーティション変更ではない。すでにマウント済みの場合は再マウント不要。環境によってはコマンドやマウント先の状態確認が必要。

**重要な限界:** 同じ所有者が別途提示した通常起動ログでは `bootslot=a`、PID1=`procd`、P43=`/data`（ext4マウント）、P44なしだった。Emergency Shellでのslotを**独立に確認できた記録はまだない**。LK接続・一時rootシェル到達は確認されたが、正規工程S03の「純正slot B Emergency Shell」完了とは異なる。**S03は未完了扱い**、S04のSSHやS05の永続化、S07の分割も未立証。

## 3. 純正Linuxの実測環境

- **CONFIRMED_ON_UNIT**: 純正slot Bで Linux **5.4.238** / **AArch64** が観測された。
- **CONFIRMED_ON_UNIT**: `init=/bin/sh` で起動したEmergency ShellはPID1が`sh`、純正rootfsは読み取り専用squashfsとして観測。通常サービスは自動起動しない。
- **CONFIRMED_ON_UNIT**: このEmergency Shellで `devtmpfs` が使えない一方、`tmpfs` と `mknod` の使用が観測された。RAM上の `/tmp` や `/dev` を準備する際は、既存ファイルを隠す再マウントを避ける。
- **CONFIRMED_ON_UNIT**: 通常起動した純正slot BではPID1=`procd`、LANのARP/pingと**公開鍵によるroot SSH**の実測がある。
- **NOT_VERIFIED**: 初期状態の任意の中古機で、上記のSSHが最初から開いていること。Emergency Shellからの一時SSH開通、純正SSH永続化の一般化された導入手順。
- **CONFIRMED_ON_UNIT / LIMITATION**: 一部B号機で純正OSの無線health監視が再起動を要求する現象を観測。通常起動後の再起動を直ちにLinux panic、OpenWrt側異常、あるいはSSH設定不備と断定しない。設定変更の個別例を初見機に一括適用しない。

**SSHの2段階の判定**:
1. 現在のブートでLAN→認証済みSSH→リモートコマンド実行まで確認したか。
2. 電源再投入または正常再起動後、同じ純正slot Bでホスト鍵・接続方式・認証状態が保持されたか。

1のみで「永続化PASS」としない。既存のroot SSHが別の開発機で動いた事実を、新規個体の認証手順として転用しない。

## 4. eMMC / GPT / P43・P44

- **CONFIRMED_ON_UNIT**: 開発機のP43はext4データ領域として観測。純正起動状態によってはマウントされるため、縮小前にはmount状態とext4/journal整合性を検査する。
- **CONFIRMED_ON_UNIT**: 分割後の実測例はP43 GPT約**453MiB**、その中のext4約**440MiB**、P44約**2.5GiB**（rootfs_data）。**パーティションのサイズとファイルシステムのサイズは異なる**。
- **EXPECTED_COMMON**: `p43` と `p44` の番号・役割は対象系統で参考になる。ただし /dev/mmcblk0 と /dev/mmcblk1 のどちらになるか、GUID、開始LBA、末尾、パーティション名は**現物から取得**し、固定文字列の流用を禁止。
- **CONFIRMED_IN_SIMULATION**: QEMUでP43約2.94GiBからext4を440MiBへ縮小し、P43 GPTを約453MiBに変更、P44を新規ext4化。200MiB試験データのSHA一致、工程境界での停止と再開を確認。
- **NOT_VERIFIED**: 未分割の第三者実機での同工程の成功、データ完全保持、電源断復旧。QEMU固定の /dev/vda・GUID・LBAを実機へ適用してはならない。
- **CONFIRMED_ON_UNIT / LIMITATION**: 分割済み機体のP43に `e2fsck -fn` が不整合を報告した事例があり、journal未再生など原因を確定していない。読み取り専用検査の非ゼロ終了を無視して自動修復・縮小してはならない。

### 保全と検証の原則

1. `/proc/cmdline` と`/sys/class/block`等で**今のブート・対象eMMC・対象P43**を同定。
2. P43が未マウントで、バックアップと復旧経路が確認できるまでは変更しない。
3. ext4縮小を先に完了・検査したうえで、GPT上のP43終端を変更する。**GPTだけ先に短くしない**。
4. P44が既に存在したら新設処理を繰り返さない。対象のデータ消去・書込み範囲を事前に明示する。
5. GPT両ヘッダとCRC、P43の整合性・保持データ、P44のext4、純正slot Bでの起動を独立に再確認する。
6. 所有者の承認は、対象個体、対象領域、バックアップ、復旧方法、予測される損失を示した後に受ける。

## 7. 純正slot Bのoverlay構造とRC16のP44設計評価（2026-11-16）

### 7.1 「この状態で問題ないか」への回答

**回答：提示された純正Linuxのmount状態は、OpenWrt系で一般的な読み取り専用rootfs＋書き込み可能overlayの構成と整合しており、表示自体に異常は見られない。**

観測されたmountは次の3層を示す。

| 観測 | 意味 |
| --- | --- |
| `/dev/root on /rom type squashfs (ro)` | 基本root filesystemがSquashFSで読み取り専用として `/rom` に見えている |
| `/dev/loop0 on /overlay type ext4 (rw)` | 書き込み可能なext4領域が `/overlay` にマウントされている |
| `overlayfs:/overlay on / type overlay (rw)` | 読み取り専用の基本rootfsと書き込み可能overlayを統合し、通常のルート `/` として提供している |

これは「基本OSを直接書き換えず、変更分を別の書き込み可能領域へ置く」構成である。したがって、mount一覧だけを見て「rootfsが二重になっている」「loop deviceだから異常」と判断する必要はない。

### 7.2 loop0とP39についての実測値

2026-11-16に提示されたsysfs値：

- loop0 backing_file：`/mmcblk0p39`
- loop0 offset：**47,841,280 bytes = 45.625 MiB**
- loop0 sizelimit：**0**（明示的な上限値なし）
- loop0 size：**168,704 sectors**
- Linux block layerの通常の512-byte sector換算：168,704 × 512 = **86,376,448 bytes = 82.375 MiB**
- P39 start：**1,187,904 sectors**
- P39 size：**262,144 sectors = 134,217,728 bytes = 128 MiB**

offsetとloop sizeの合計は **47,841,280 + 86,376,448 = 134,217,728 bytes** で、P39の報告サイズ128 MiBと一致する。したがって、提示値は「P39相当の128 MiB領域のうち、先頭から45.625 MiB進んだ位置に82.375 MiBのloop領域がある」という配置と算術的に整合する。

**注意：** この結果だけでは、P39先頭側45.625 MiBの用途までは確定しない。特に、その部分をSquashFSと断定しない。SquashFSとして直接確認できているのは、mount上の `/dev/root on /rom` である。また、`backing_file` の文字列は `/mmcblk0p39` と報告されているが、そのパスの実体種別やデバイスへの結び付きは、この出力だけでは完全には検証していない。

### 7.3 RC16でP43を縮小し、P44を新設した設計上のメリット

**結論：P43/P44の再配分は、eMMCの総容量を増やす操作ではない。既存のP43領域の一部を、OpenWrt専用の大容量・永続overlayへ振り替える設計である。**

純正構成で観測されたloop overlayは約**82.375 MiB**。RC16設計のP44は約**2.5 GiB（約2,560 MiB）**で、容量だけを比べると約**31.1倍**になる。これはパッケージだけでなく、設定、追加プログラム、その他root filesystem上で永続化する変更を置く余地を大きくする。

主な設計メリット：

1. **パッケージ拡張の余地：** `apk add` で導入したファイルは通常のroot filesystem配下（例：`/usr`、`/lib`、`/etc`）に展開される。基本rootfsが読み取り専用であれば、新規ファイルや変更分はoverlayの書き込み側に置かれる。P44をoverlayのupper領域として使うことで、純正観測の約82.375 MiBより大きな保存領域を確保できる。
2. **基本OSと可変データの分離：** P26を基本rootfs、P44を書き込み可能なoverlayとして分離する。P26の内容を変更せず、追加パッケージや設定変更をP44側へ集約できる。
3. **P43の役割を残す：** P43を約453 MiBの `user_data` として残し、既存データを保持する設計とする。P43全体をOpenWrtのoverlayに転用するのではなく、純正データ領域とOpenWrtの書き込み領域を分ける。
4. **保守・検証の境界を明確化：** P26（基本OS）、P43（既存user_data）、P44（OpenWrtの永続overlay）を別領域として扱える。バックアップ、容量監視、ファイルシステム検査、更新時の保持対象を分けて考えやすい。
5. **実験環境としての余裕：** Wi-Fi、モデム、GPS、Bluetooth、ネットワーク診断などの機能を追加していく際、容量不足によって毎回パッケージを選別・削除する制約を減らせる。

この設計は「2.5 GiBをAPKアーカイブ専用に確保する」という意味ではない。P44がoverlayのupper領域なら、インストール済みパッケージの実ファイル、パッケージ管理データベース、設定変更、追加ファイルなどが保存対象となる。ダウンロードした `.apk` アーカイブやリポジトリ索引のキャッシュは別扱いで、設定・実装によって保存先が異なる。

### 7.4 トレードオフと成立条件

- P43を縮小しているため、P43に残せる純正データ容量は減る。これは無償の容量増加ではなく、既存領域の再配分である。
- P43の縮小・GPT変更は破壊的操作になり得る。対象個体の完全バックアップ、ext4整合性、GPT主副の検査、独立readback、復旧手段が必要。
- P44を作成・ext4化しただけではoverlayとして機能しない。起動時にP44を正しくマウントし、OverlayFSのupper/workとして採用する統合が必要。
- P44を使う設計が正しく機能しているかは、`/overlay` の実体、OverlayFSのupper/work、再起動後の設定保持、パッケージ導入後の保持を別々に確認する。
- P44の容量はパッケージ専用ではなく、overlayに書き込まれる全データで共有する。キャッシュ、`/tmp`、別パーティションへの保存は別の容量管理となる。
- P43/P44の役割やGPT値は、すべての個体・ファームウェアで同一とは限らない。現物の読み取り専用調査とバックアップを省略しない。

**総合評価：** P44を約2.5 GiBの永続overlayとして使う方針は、パッケージ追加と継続的な機能開発を行うRC16の目的に対して合理的である。ただし、その評価は「P44が実際にroot OverlayFSのupper/workとして使われ、再起動後もデータが保持される」ことを条件とする。P43縮小の安全性や、純正機能・OTAへの影響まで一般化して保証するものではない。
